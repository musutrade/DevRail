# PostgreSQL 备份、PITR 与恢复演练

## 目标

上线前由业务负责人确认 RPO/RTO。模板建议起点为 RPO 不超过 15 分钟、RTO 不超过 4 小时；资金、Token 流转或关键 OA 审批应采用更严格目标，并据此选择托管 PostgreSQL、跨区域复制和备份频率。

## 备份组合

- 每日执行一次 `pg_dump --format=custom` 逻辑备份，保留至少 30 天，用于表级检查和小规模恢复；
- 每周执行一次 `pg_basebackup` 基础备份，连续归档 WAL，形成任意时间点恢复链；
- 备份在传输和存储时加密，复制到与数据库不同的账号及故障域，启用对象锁或不可变保留；
- 每份备份保存 SHA-256、开始/结束时间、PostgreSQL 版本、数据库名和最后归档 WAL；
- 备份账号只授予所需读取与复制权限，凭据通过密钥系统注入，不写入脚本或仓库。

生产 Compose 已启用数据校验和、`archive_mode`、5 分钟 `archive_timeout`，并把 WAL 暂存到 `postgres-wal-archive` 卷。运维任务必须把新 WAL 原子上传到远端，确认远端校验成功后再按保留策略清理本地归档。

## 恢复流程

1. 宣布事件并冻结写入，记录目标恢复时间和当前 WAL 位置；不得直接覆盖唯一的生产实例。
2. 在隔离网络创建相同 PostgreSQL 大版本的新实例，下载最近的完整基础备份并校验哈希。
3. 配置 `restore_command` 从远端归档取回 WAL，并设置 `recovery_target_time` 或目标 LSN；启动实例直到达到目标点并自动结束恢复。
4. 执行一致性检查：迁移版本、关键表计数、最近业务流水、外键、登录与权限边界；Token/资金系统还需执行总账对账。
5. 由业务负责人确认数据点后切换连接串，保持旧实例只读，观察错误率、延迟和审计日志。
6. 事件结束后补齐缺失 WAL、轮换临时凭据并形成复盘。

只有逻辑备份时，使用全新空库执行 `pg_restore --clean --if-exists`。这类恢复不能达到 WAL 级 RPO，不应替代 PITR。

## 演练与证据

至少每季度执行一次完整恢复演练，每月抽查一次逻辑备份可读性。演练不能连接生产数据库，必须恢复到隔离实例，并记录：

- 使用的基础备份和 WAL 范围；
- 实际数据丢失窗口与恢复耗时，对比目标 RPO/RTO；
- 哈希校验、`pg_verifybackup`、迁移状态和业务验收结果；
- 失败步骤、负责人、整改截止日期和下一次复测时间。

连续两次演练未达到目标时，应停止扩大生产负载，优先修复备份链、网络吞吐或恢复自动化。未经过恢复验证的备份不能视为可用备份。
